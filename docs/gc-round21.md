# GC-счётчики и weakrefs (раунд 21, wave w_gc)

## Что сделано

### 1. Счёт gc_collect_cycles() по модели Zend (internal/vm/lifetime.go)

Zend считает «белые» узлы, собранные из буфера возможных корней, и не
учитывает узлы, умершие по refcount (они уничтожаются в точке записи).
В VM введены эквивалентные правила:

- **Каскад indeg==0 больше не считается**: это смерть по refcount, Zend
  уничтожает такие узлы в точке записи (не в gc_collect_cycles).
- **gcNested** (`Object.gcNested`): объект, чей счётчик достиг нуля внутри
  выполняющегося `__destruct` (каскад по refcount), уничтожается, но не
  входит в возвращаемое число (gc_017/gc_028/gc_029).
- **Воскрешение**: если после фазы деструкторов узел снова достижим от
  корней (`$GLOBALS['x'] = $this`), он снимается со счёта вместе с
  поддеревом (gc_041, `gcUncountResurrected` + `lifeVisit.reachDead`).
- **Устаревшие регистрации само-циклов** проверяются `arrayCyclic` с чистыми
  картами: отвязанная ссылка снимает цикл, массив не считается (gc_020),
  а порядок map-итерации не «поглощает» циклический мусор (gc_022).
- **Нативные массивы** собранных объектов (storage ArrayObject/ArrayIterator
  и т.п.) считаются отдельными белыми узлами (`walkObjectNativeArrays`,
  gc_024); `walkReflect` видит ссылки из нативных полей-массивов.
- **unserialize** регистрирует само-циклы (`R:`-ссылка на сам массив):
  `phpUnser.setArr` → `VM.NoteRefCycle` (gc_022).

### 2. gc_status() и ошибки (internal/php/builtins_misc.go)

- runs/collected теперь ведёт VM (`gcRuns`/`gcCollected`), сброс — в Init
  (раньше были package-global и протекали между .phpt).
- `CollectCycles()` возвращает `(int, error)`: исключение из `__destruct`
  поднимается в вызывающий код (error-протокол, gc_030) вместо потери.
- Деструкторы в проходе продолжают вызываться и после исключения; исключения
  сцепляются через `previous` (`chainPrevious`).
- Новое: печать цепочки непойманных исключений («\nNext Exception: …»,
  суффикс «  thrown in …» у последнего) — `uncaughtChain`/`writeUncaughtChain`
  в vm.go (gc_030, exception_007, throwable_001).

### 3. Чтение ссылок = снимок (bug72543_3/4/5)

Отвязанная ячейка-ссылка портила «прочитанный до записи» операнд:
`$x->a + ($x->a = 2)` давало 4 вместо 3. Снимок делается там, где Zend
разыменовывает при чтении:

- `OpIndex` (чтение элемента массива) возвращает снимок значения
  (`snapReadVal`), как FETCH_DIM_R;
- бинарные операции компилируют операнд-свойство через `binOperand`:
  после `PROP_GET` эмитится `REF_GET` (снимок), как FETCH_OBJ_R;
- write-контексты (`++/--`, составное присваивание) читают базу
  `OP_INDEX_RAW`/`RW`-опкодами и сохраняют ячейку — иначе терялись guard
  переполнения типизированного свойства и запись через ссылку
  (bug64417, typed_properties_062/064/065).

### 4. Прочее

- `mb_parse_str` — как parse_str, но возвращает true (gc_039).
- SPL: `FilterIterator` (абстрактный) + `CallbackFilterIterator` с
  предикатом-замыканием (gc_046).
- `chainPrevious` не создаёт цикл, если исключение уже есть в цепочке
  previous (try_finally_recursive_previous).

## Что осталось (осознанно не тронуто)

- **bug70805/1/2, gc_023, gc_037, gc_045** — нужен буфер возможных корней
  Zend (10001 записей, добавление на каждом декременте до положительного
  refcount, автоматический сбор при переполнении, динамический threshold,
  roots/runs/collected в gc_status). В VM такого буфера нет: циклы
  собираются только по явному gc_collect_cycles().
- **gc_043** — требует `C:`-unserialize для SplStack/SplDoublyLinkedList
  (Serializable) и RegexIterator.
- **gc_047** — by-ref foreach + `$a =& $b` внутри цикла: глубокий случай
  регистрации циклического мусора при ребиндe ссылки.
- **bug72543** — COW: при копировании массива с «одинокой» ссылкой Zend
  разворачивает её в значение; в VM копия делит ячейку.
- **weakmap_weakness** (weakrefs) — порядок переиспользования PHP-хендлов в
  каскаде WeakMap; не трогал, чтобы не сломать существующие handle-тесты.

## Инварианты

- Исключения — error-протокол (никаких panic; после Throw — guard/return).
- Writeback/entryNull не переделывались: `markFrameRegs` по `f.tracked`,
  `chunk.entryNull`, `wRegSlow/wDropReg/nTracked/dropFrame/OpSweep` — как были.
- В горячие точки добавлены только проверки типа для снимка чтения элемента
  (`snapReadVal` в OpIndex — одно сравнение) и `REF_GET` для операндов-
  свойств бинарных операций (эмитится компилятором); сборщик обычное
  исполнение не замедляет.
